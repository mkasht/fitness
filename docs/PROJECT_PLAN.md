# План разработки сайта фитнес-центра

Исторический план первой версии. Текущая структура и запуск описаны в [README проекта](../README.md).

План обновлён: 6 ноября 2026 года. Рабочий срок разработки: два дня, 6–7 ноября. Крайний срок сдачи по ТЗ: 14 ноября 2026 года.

Основание: praktika.docx, вариант 9. Референс: https://flightfitness.ru/.

Цель: разработать сайт фитнес-центра с каталогом услуг и тренеров, записью на тренировки, личным кабинетом и панелью управления для администратора и менеджера.

## 1. Технологии и организация приложения

Предлагаемый стек:

| Часть | Решение | Назначение |
| --- | --- | --- |
| Платформа | .NET 10 LTS и ASP.NET Core | Запуск веб-приложения |
| Интерфейс | Blazor Web App | Страницы и интерактивные компоненты на C# |
| Режим отображения | Серверный рендеринг публичных страниц, Interactive Server для записи и управления | Быстрая выдача контента и интерактивность форм |
| Оформление | Razor, HTML и собственный CSS | Адаптивный дизайн |
| Пользователи | ASP.NET Core Identity | Регистрация, вход, хеширование паролей, роли |
| Доступ к данным | Entity Framework Core 10 | Модели, запросы и миграции базы |
| База данных | SQL Server Express, LocalDB для локальной разработки | Хранение данных и проверка конкурентных изменений |
| Проверки | xUnit и интеграционные тесты | Проверка правил записи и доступа |
| История изменений | Git | Фиксация законченных этапов |

Серверная логика, обработка действий пользователя и проверки пишутся на C#. Для веб-интерфейса необходимы разметка Razor/HTML и CSS. Отдельное приложение на JavaScript не планируется; Blazor использует собственные браузерные компоненты платформы. Карту можно подключить через iframe.

.NET 10 SDK уже установлен на компьютере. Наличие SQL Server и подходящей среды разработки нужно проверить на первом этапе.

Архитектура: одно веб-приложение с выделенными сервисами для бизнес-правил и отдельным проектом тестов. Публичный сайт, личный кабинет и панель управления работают с общей базой. Отдельный API для этой версии не требуется.

Предлагаемая структура:


В интерактивных компонентах создавать короткоживущий контекст базы для каждой операции через фабрику DbContext, чтобы не разделять один контекст между длительными пользовательскими сессиями.

## 2. Как использовать референс

На сайте Flight представлены направления тренировок, подробные услуги, тренеры, расписание, контакты и повторяющиеся предложения записаться. Для нашего проекта используем эту логику подачи информации.

Предлагаемое визуальное направление: крупные фотографии тренировок, выразительные заголовки, контрастные кнопки, свободное пространство и единый акцентный цвет. Конкретные цвета, шрифты и название зафиксировать при подготовке первого макета.

Главная страница:

1. Шапка: логотип, меню по ТЗ, контакты и вход в личный кабинет.
2. Большой баннер со слайдами: преимущества центра, акция, популярная услуга; кнопка «Записаться».
3. Блок «О нас»: миссия, инфраструктура, квалификация команды.
4. Основные услуги: карточки с фотографией, описанием и переходом на страницу услуги.
5. Тренеры: фотография, имя, специализация и переход в профиль.
6. Опубликованные отзывы и ссылка на полный раздел.
7. Форма записи с выбором даты, времени и тренера.
8. Контакты, часы работы и карта.
9. Подвал: повторное меню, социальные сети, разработчики и ссылка на распределение задач.

Фотографии, тексты, логотип и контактные данные подготовить для собственного учебного центра. Состав услуг выбрать в объёме, достаточном для демонстрации всех сценариев ТЗ. Дополнительные разделы референса, например магазин или журнал, в обязательную версию не включать.

## 5. Правила записи и права доступа

Основной сценарий: услуга → тренер → дата → доступное время → подтверждение пользователем → обработка менеджером → посещение → отзыв.

Предлагаемые правила для первой версии:

- Просматривать занятия можно без входа, создавать запись — после авторизации. Выбор занятия сохраняется при переходе на страницу входа.
- Расписание состоит из конкретных занятий с началом и окончанием. У индивидуального занятия вместимость 1; у группового — заданное число мест.
- Администратор не может создать пересекающиеся занятия для одного тренера.
- Нельзя записаться в прошлое, на отменённое занятие, дважды на одно занятие или на пересекающиеся по времени занятия.
- Статусы заявки: «Ожидает подтверждения», «Подтверждена», «Отклонена», «Отменена», «Посещено», «Неявка».
- Ожидающая и подтверждённая заявки занимают место; отклонение или отмена освобождают его. Менеджер регулярно обрабатывает ожидающие заявки.
- При одновременной записи нескольких пользователей число занятых мест не превышает вместимость. Проверку и сохранение выполнять атомарно в базе с защитой от конкурентных изменений и повторной отправки формы.
- Пользователь может отменить свою активную запись до начала занятия. Перенос выполняется отменой и новой записью.
- Посещение или неявку фиксирует менеджер либо администратор после окончания занятия.
- Один отзыв допускается на одну посещённую запись. Публикация — после одобрения администратором.
- Изменение времени, тренера или вместимости занятия с активными записями запрещено в первой версии; использовать отмену с уведомлением и создание нового занятия.
- Время показывать в часовом поясе центра, который задаётся в настройках.

Проверять права в серверных обработчиках и сервисах, а не только скрывать элементы меню. Пользователь не получает чужие записи по подменённому идентификатору. Менеджер не меняет контент, роли и профили пользователей. Назначение роли тренера не требуется: по ТЗ тренер представлен профилем в каталоге.

Как удерживаем темп:

- Используем готовую основу Identity и общие компоненты форм, карточек и таблиц.
- Пишем бизнес-правила в сервисах, которые используют и сайт, и панель управления.
- Сразу заполняем базу демонстрационными данными, чтобы проверять реальные сценарии.
- Визуальное направление выбираем в начале и последовательно применяем на всех страницах.
- После каждого законченного блока проверяем запуск и фиксируем результат; обязательные проверки не откладываем целиком на конец.

Если блок занимает больше ожидаемого, пересматриваем оставшуюся последовательность по фактическому прогрессу и явно фиксируем незавершённые функции. Завершённость проекта определяется критериями приёмки, а не истечением двух дней.

## 7. Проверки и критерии приёмки

Автоматические проверки направить на правила, при ошибке которых портятся данные или нарушается доступ:

1. Одновременная заявка двух пользователей на последнее место: проходит только одна.
2. Повторная отправка заявки не создаёт дубликат.
3. Запись в прошлое, на отменённое или заполненное занятие отклоняется.
4. Пересекающиеся занятия тренера и пересекающиеся записи пользователя отклоняются.
5. Отмена и отклонение освобождают место; число мест остаётся корректным при конкурентных операциях.
6. Запрещённые переходы статусов и отметка посещения до окончания занятия отклоняются.
7. Пользователь не читает и не изменяет чужие записи; менеджер не назначает роли.
8. Отзыв без посещения не принимается, повторный отзыв на ту же запись не создаётся, неопубликованный отзыв не виден на сайте.

Проверки транзакций и конкурентных операций выполнять на SQL Server, чтобы они отражали поведение выбранной базы, а не её упрощённой имитации.

Ручная приёмка:

- Все страницы из ТЗ существуют отдельно и открываются из меню.
- Главная содержит каждый предусмотренный блок, включая запись и информацию о разработчиках.
- Пройден сценарий: регистрация → выбор занятия → заявка → подтверждение → посещение → отзыв → модерация → публикация.
- Проверены роли администратора, менеджера, пользователя и посетителя без входа.
- На ширинах 360, 768 и 1440 пикселей отсутствует горизонтальная прокрутка; меню, формы и таблицы остаются удобными.
- Формы объясняют ошибки, сохраняют введённые данные после ошибки и блокируют повторную отправку во время сохранения.
- Пароли обрабатываются Identity; секреты не находятся в исходном коде; изменяющие запросы защищены; загрузка изображений ограничена по размеру и формату.
- Кешируются публичные справочники и статические файлы, изменения контента сбрасывают соответствующий кеш. Личный кабинет и персональные данные не попадают в общий кеш.
- Изображения сжаты и имеют подходящие размеры; второстепенные изображения загружаются отложенно; CSS минимизирован, статические ресурсы сжимаются при передаче.
- Страницы проверены в двух браузерах; при потере соединения интерактивный интерфейс показывает понятное состояние восстановления.
- Приложение запускается по инструкции с новой базой, миграции применяются, демонстрационные записи доступны.

## 8. Работа команды

Если проект выполняется командой, распределить ответственность по направлениям: интерфейс и контент; база и запись; учётные записи и панель управления; проверка и документация. Число участников и имена пока неизвестны, поэтому конкретных исполнителей назначить после определения состава команды.

При работе пользователя с Codex это последовательные направления двухдневного плана. Проверять запуск и фиксировать работающий этап в Git после каждого завершённого блока. Страницу распределения задач заполнить реальными именами и фактическим вкладом до сдачи.
